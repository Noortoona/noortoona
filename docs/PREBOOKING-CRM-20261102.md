# HALA — الحجوزات المسبقة والعملاء والإحصائيات

تاريخ العمل: 2 نوفمبر 2026. الفرع: `hala-prebooking-crm-20261102`، انطلاقًا من `a90add8`.

## الحالة الفعلية ونطاق التسليم

أُضيف نظام مستقل للحجوزات المسبقة إلى المشروع القائم؛ لم يُعد بناء المشروع، ولم تتغير ملفات الشعار المعتمدة أو الهوية. لم تُطبق هذه الترحيلات على إنتاج، ولم يُدمج الفرع في main أو يُنشر على الموقع الإنتاجي.

الرحلة الجديدة تحفظ الحجز في PostgreSQL، وتعيد رقمًا فريدًا مثل `HALA-XXXXXXXXXXXX`، وتفصل `pre_booking_received` عن `pending_payment`. لا تطلب دفعًا أو فتح واتساب لإكمال التسجيل. التسعير والإحالة والخصم تُراجع في الخادم من الكتالوج الحقيقي؛ تُحفظ لقطة المناسبة والتصميم والخدمات والسعر. لا تُنشأ عمولة مستحقة بمجرد الحجز.

يوجد مسار عميل زائر مع رمز وصول عشوائي محفوظ على جهازه، ومسار عميل مسجل. رمز الوصول يُرسل في ترويسة الطلب ولا يظهر في رابط الحجز. يمكن ربط حجز الزائر بحسابه عند فتحه من الجهاز الذي يحتفظ بالرمز بعد تسجيل الدخول. الانتقال إلى جهاز آخر دون حساب مرتبط لا يستعيد الرمز تلقائيًا؛ ليس رقم الحجز وحده مفتاحًا لقراءة البيانات.

## الحفظ والصلاحيات

تُحفظ الحجوزات والإشعارات الداخلية وسجل التدقيق ضمن معاملة واحدة. قفل المعاملة ومفتاح idempotency والقيد الفريد للمناسبة يمنعون تكرار الحجز؛ إعادة الطلب نفسه تعيد السجل الأصلي. اختلاف بيانات الطلب تحت المفتاح نفسه يرفض بـ409. سعر قديم في الواجهة يُرفض عند اختلافه عن حساب الخادم.

لوحة الحجوزات تقرأ السجلات الفعلية، وتوفر البحث وتصفية الحالة والدفع والتصدير وتعيين الموظفة والملاحظات وآخر متابعة والموعد القادم. تُعرض حالات الدفع مستقلة. دور `customer_service` يقرأ الحجوزات والعملاء والمؤشرات ويحدّث المتابعة؛ لا يغيّر الأسعار والإعدادات الحساسة أو يعتمد سدادًا. أُضيف للإدارة نموذج إنشاء حساب موظفة حقيقي؛ لم نختلق اسم موظفة أو جوالها ولم نغيّر حسابات إنتاج.

سجل العملاء يوحد وسيلة التواصل داخل البيئة، ويربط الحجوزات المطابقة. بيانات نموذج الاهتمام هي بيانات أدخلها صاحب الطلب وليست موثقة تلقائيًا بـOTP. الموافقة التسويقية مستقلة وغير مطلوبة للحجز أو لتسجيل الاهتمام؛ لم تُرسل رسائل تسويق.

## مصدر كل مؤشر

كل الاستعلامات الجديدة مقيدة بالبيئة. الإنتاج `production`، والمعاينات `preview:<branch>`، والسجلات التاريخية التي لا تثبت بيئتها تبقى `legacy_unclassified`؛ لا تُنقل اعتباطيًا إلى أرقام الإنتاج.

| المؤشر | المصدر والحساب |
|---|---|
| مشاهدات الصفحات | عدد سجلات `page_views` ذات `event_name=page_view`؛ ليست عدد أشخاص |
| اليوم / 7 أيام / 30 يومًا | السجلات نفسها مع حدود زمنية؛ اليوم بتوقيت الرياض، والمدد الأخرى متحركة |
| الجلسات | `COUNT(DISTINCT session_id)` لمشاهدات الصفحات؛ المتصفح يجدد الجلسة بعد خمول 30 دقيقة |
| الزوار الفريدون تقديريًا | معرّفات متصفح `visitor_id` المميزة بعد الموافقة؛ لا تعادل أشخاصًا مؤكدين |
| الصفحات والمصادر والأجهزة | تجميع سجلات المشاهدات حسب المسار وUTM/مضيف الإحالة ونوع الجهاز المستنتج؛ المصدر غير المثبت مباشر/غير معروف |
| أحداث الاهتمام | أحداث فعلية غير `page_view`؛ إكمال الحجز والتواصل والاشتراك تُثبت من الخادم |
| العملاء المعروفون | سجلات التواصل في `leads`؛ الاهتمام المستقل يستبعد الصفوف التي أُنشئت للحجز فقط |
| إجمالي الحجوزات وحالاتها | سجلات `bookings` المحفوظة، وليس نقرات زر التأكيد |
| القيمة المحتملة | مجموع `total_amount` للحجوزات بانتظار الدفع وغير الملغاة، بالهللات |
| الإيراد المحقق | مجموع `payment_orders.amount` بحالة paid ونمط live وفي البيئة نفسها؛ يستبعد الاختبار والمجهول |
| متوسط الطلب | متوسط `bookings.total_amount` لجميع الحجوزات في البيئة، بما فيها الملغاة؛ لا يُسمى متوسط المبيعات |
| زيارة ← بدء الحجز | الجلسات ذات مشاهدة وبدء حجز / جلسات المشاهدات |
| إكمال الحجز | جلسات البدء التي تلاها إكمال مثبت من الخادم / جلسات البدء |
| مهتم معروف ← حجز | سجلات الاهتمام المستقلة ذات حجز يطابق وسيلة التواصل / سجلات الاهتمام المستقلة |
| حجز مسبق ← دفع | الحجوزات المدفوعة / جميع الحجوزات المحفوظة |

التتبع اختياري بموافقة منفصلة. غير الموافقين لا يدخلون مؤشرات الزيارات، لكن حجوزاتهم المحفوظة تدخل مؤشرات الحجوزات. لذلك لا يُفترض أن حجم المرور المرصود يشمل كل الزوار. يوجد تقييد للطلبات، تجاهل أولي لوكلاء الزيارات الآلية، منع تكرار event_id وتقييد الاندفاع في الجلسة؛ ليس ذلك إثباتًا أن كل زيارة بشرية. لا تُحفظ استعلامات URL أو بيانات التواصل في metadata التحليلات. بيانات UTM المعلنة ليست إثباتًا لهوية مرسلها؛ الإحالة التجارية تعتمد كود شريك نشط متحقق منه.

## واتساب

الرقم الافتراضي `966532763736` قابل للتعديل من إعدادات الإدارة دون تعديل الكود. زر الدعم يجهز رقم الحجز داخل نص الرسالة؛ ليس آلية إرسال آلي.

الإشعار الداخلي يُنشأ قبل محاولة الإرسال الخارجي. الحالة الافتراضية للإشعار الخارجي `pending_setup` / «بانتظار إعداد واتساب». المسار الرسمي مهيأ لقبول مزود 360dialog فقط؛ لا يدّعي التسليم عند قبول API، بل يبقى queued حتى دليل webhook. أحداث sent/delivered/read تُحدث تصاعديًا، وأخطاء المزود تُسجل. فشل الإشعار لا يلغي الحجز.

متطلبات تفعيل الإشعار الحقيقي في البيئة المستهدفة:

- إعداد API وwebhook الموثق القائم، ومعرفة نمط المزود production أو sandbox.
- `HALA_BOOKING_NOTIFICATIONS_ENABLED=true`، `D360_BOOKING_TEMPLATE_APPROVED=true`، `HALA_BOOKING_NOTIFICATION_RECIPIENT_CONFIRMED=true`.
- `D360_BOOKING_TEMPLATE` مع قالب معتمد ومتوافق مع معاملات الرسالة، و`D360_SENDER_PHONE` برقم إرسال صالح ومختلف عن رقم استقبال الإشعار.
- المعاينة تحتاج تفعيلها صراحة عبر `HALA_BOOKING_NOTIFICATIONS_PREVIEW=true` مع sandbox.

لم يُختبر إرسال حقيقي إلى هاتف أو حساب إنتاج في هذه الجلسة؛ اختبارات المزود محاكاة مع قاعدة بيانات حقيقية محلية. يوجد إجراء إداري لمعالجة إشعار بانتظار الإعداد بعد استكمال المتطلبات. لا تعاد محاولة حالة مهلة إرسال غير مؤكدة آليًا لتجنب إرسال مكرر؛ يلزم مطابقة الحالة مع المزود أولًا. لا توجد مهمة إعادة محاولة دورية لهذا المسار حاليًا.

## الدفع والشراكات

لم يُفعّل تحصيل حقيقي ولم تُنشأ معاملات مالية على الإنتاج. يمكن لمسار ميسر القائم مستقبلًا استخدام الحجز المحفوظ وسعره بدل إعادة إنشاء الدعوة أو إعادة تسعيرها من كتالوج تغير لاحقًا. تأكيد السداد يأتي من تحقق الخادم، ثم تتحدث حالة الدفع والحجز ويستمر سجل عمولات الشركاء القائم. يمنع قيد قاعدة البيانات أكثر من أمر دفع نشط للحجز. هذا تجهيز برمجي؛ يتطلب اعتماد إعدادات ميسر وبيئة اختبار متصلة والتحقق من webhook قبل السماح بالدفع الحقيقي.

تُحفظ إحالة القاعة/المؤثر مع الحجز. احتساب خصم المؤثر والعمولة يتبع قواعد المشروع الحالية، ولا تتكون عمولة مستحقة بمجرد الطلب غير المدفوع.

## طريقة المراجعة

1. جهز معاينة Netlify بقاعدة بيانات منفصلة، وطبق الترحيلين عبر مسار ترحيلات المشروع. لا توجّه المعاينة لقاعدة الإنتاج.
2. اترك الدفع الحقيقي وإشعارات الهاتف الفعلية معطلة، ثم افتح الرئيسية بكود UTM تجريبي داخل المعاينة فقط.
3. أكمل المناسبة والتصميم والتاريخ والموقع والعدد والخدمات وبيانات التواصل، وراجع سعر الخادم واضغط «تأكيد طلب الحجز».
4. تحقق من رقم الحجز وحالة الدفع، وأعد تحميل «عرض حجزي» دون وجود رمز سري في الرابط. أعد نفس طلب API بمفتاحه للتحقق من عدم التكرار.
5. ادخل بحساب إدارة اختبار، وراجع الحجوزات والإشعار الداخلي والإحالة والتصدير؛ أنشئ موظفة اختبار داخل قاعدة المعاينة فقط وتحقق من حدود دورها.
6. سجل اهتمامًا مستقلًا دون موافقة تسويق، وراجع CRM. فعّل موافقة القياس عند اختبار مسار الأحداث؛ تحقق من أصفار الإيرادات قبل وجود سداد live متحقق منه.
7. في التطبيق، اضبط عنوان API على المعاينة ثم اختبر الحجز كزائر، حفظ الرمز في SecureStore، الرجوع للطلب، ولوحة الموظفة على جهاز فعلي.

## بوابات المراجعة المتبقية

هذه نسخة تطوير مختبرة محليًا، وليست إعلان جاهزية إطلاق نهائية. يلزم تحقق المعاينة المتصلة بقاعدة منفصلة، اختبار التطبيق على أجهزة iOS وAndroid فعلية، التوقيع والبناء إن توفرت متطلباته، واختبار المزود الحقيقي المعتمد. لم تُثبت في هذه الجلسة صلاحية اشتراك Apple أو شهادات التوقيع.

هناك خدمات كتالوج وصفية لا تملك سعرًا آليًا في البنية الحالية؛ الحجز يدعم الباقة وخدمة المشرف المسعّرة، ولا يختلق أسعارًا للخدمات الأخرى. مسودة مناسبة أُنشئت ثم تغيرت بياناتها بعد فشل الشبكة تحتاج مراجعة اتساق قبل الإطلاق؛ تفاصيل الحجز الموثوقة هي لقطة الخادم المحفوظة. لا توجد حاليًا آلية استرداد حجز زائر عبر جهاز آخر دون رمز الجهاز أو حساب مرتبط. يجب مراجعة هذه الحدود عند تجربة المعاينة.
